# Root cause & options — AWS credential modes for the S3 content cache

> **One-line summary:** the MITM service's S3 content cache only works when the
> container is given **explicit long-lived static AWS keys**. It does not work with the
> **EC2 instance role (IMDS)** nor with **temporary STS credentials (`AWS_SESSION_TOKEN`)**.
> This document pins the root cause to the upstream `osbot-aws` client builder and
> documents the available fix options. **No fix is applied here** — this is analysis only.

---

## 1. The request (from the content_proxy team)

Make the MITM service resolve AWS credentials through boto3's **default provider chain** so
it works in all three modes, selected purely by which env vars are present:

| # | Mode | Env provided | Primary use |
|---|------|--------------|-------------|
| **1** | **Ambient role** (default) | *no* `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | EC2 instance role / Fargate task role / Lambda exec role — **production default**, auto-refreshing |
| **2** | **Static long-lived keys** | `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` | Laptop / CI with an IAM user key |
| **3** | **Temporary STS creds** | `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` + **`AWS_SESSION_TOKEN`** | Forwarded `sts assume-role` / SSO / instance-role creds |

Region comes from `AWS_DEFAULT_REGION` / `AWS_REGION`. The full upstream brief is
`v0.2.64__cp-mitm-service__aws-credential-modes`.

## 2. Where the credentials are actually resolved (the boundary)

**This repository (`mgraph-ai-service-mitmproxy`) contains zero boto3 / AWS-credential
code.** A full-repo search for `boto3`, `botocore`, `aws_access_key_id`,
`AWS_ACCESS_KEY_ID`, `aws_session_token`, etc. returns no matches in any `.py` file.

The S3 access flows through a dependency, in-process:

```
Proxy__Cache__Service.cache_client : Cache__Service__Client     # service/cache/Proxy__Cache__Service.py:24
    └─ mgraph_ai_service_cache_client            (cache I/O facade)
        └─ mgraph-ai-service-cache               (in-memory S3 backend)
            └─ osbot-aws 2.39.10                 (builds the boto3 S3 client)   <-- root cause lives here
                └─ boto3 1.42.36
```

- `CACHE__SERVICE__BUCKET_NAME` is only **forwarded as an env var** at deploy time
  (`mgraph_ai_service_mitmproxy/utils/deploy/Deploy__Service.py:37`). Nothing in this repo
  opens an S3 client.
- The cache runs **in-memory** (the remote/HTTP `setup__service_auth()` path in
  `Proxy__Cache__Service.py:36-59` is commented out), so the cache service's own code — and
  therefore `osbot-aws` — builds the boto3 S3 client inside this container.

`Cache__Health_Check__Service.py` is a red herring (pure HTTP `requests.get`, no S3).
`lambda_handler.py:5` only uses `osbot-aws` for Lambda dependency loading, not the cache path.

## 3. Root cause — pinned to exact `osbot-aws 2.39.10` code

The S3 client is assembled across three files:

**`osbot_aws/aws/s3/S3.py:47-48`** — the client constructor:
```python
@cache_on_self
def client(self):
    return self.session().client(**self.session_kwargs__s3.__locals__())
```

**`osbot_aws/aws/session/Session__Kwargs.py:4-7`** — the kwargs bundle handed to it:
```python
aws_access_key_id     : str = None
aws_secret_access_key : str = None
endpoint_url          : str = None
region_name           : str = None
```
→ **There is no `aws_session_token` field.** The bundle structurally cannot carry a token.

**`osbot_aws/apis/Session.py` → `client_boto3()`** — the actual boto3 builder used by S3:
```python
def client_boto3(self, service_name, aws_access_key_id=None, aws_secret_access_key=None,
                 region_name=None, config=None, endpoint_url=None, profile_name=None):
    ...
    if aws_access_key_id    : client_kwargs['aws_access_key_id'    ] = aws_access_key_id
    if aws_secret_access_key: client_kwargs['aws_secret_access_key'] = aws_secret_access_key
    if self.endpoint_url    : client_kwargs['endpoint_url'         ] = self.endpoint_url
    if self.region_name     : client_kwargs['region_name'          ] = self.region_name
    ...
    client = boto3.client(**client_kwargs)
```
→ **No `aws_session_token` parameter** — it is neither accepted nor passed to `boto3.client(...)`.

### Behaviour per mode in this version

| Mode | Result | Why |
|------|--------|-----|
| **2 — static keys** | ✅ works | keys are truthy → passed to `boto3.client(...)` |
| **1 — ambient role / empty keys** | ✅ *should already work* | the `if aws_access_key_id:` guards treat `""`/`None` as **falsy** → keys are **skipped** → `boto3.client('s3', …)` falls through to botocore's **default provider chain** → IMDS/role resolves |
| **3 — temporary STS creds** | ❌ **broken** | even with key+secret passed, the **session token is silently dropped** (no field, no param) → AWS rejects temp credentials, which require the token |

### Two corrections to the original hypothesis

1. **The empty-string trap is already mitigated** at the `osbot-aws` layer. The brief (§5.2)
   worried that `aws_access_key_id=""` would be passed to boto3 and break resolution. In
   2.39.10, the `if aws_access_key_id:` truthiness guard **skips** empty strings, so they fall
   through to the default chain rather than breaking it. Mode 1 *at this layer* should work.

2. **The definitively provable bug is mode 3** (the dropped `AWS_SESSION_TOKEN`). If mode 1
   genuinely fails in production, the explicit keys must be injected **upstream** (in
   `mgraph-ai-service-cache-client`, which populates `Session__Kwargs__S3` from env), or a
   stale non-empty key is being passed. That upstream package could not be inspected during
   this analysis (it requires Python ≥3.12, unavailable in the analysis environment) — see §6.

### Auto-refresh note

`S3.client()` is `@cache_on_self`, and `Session.session()` / `botocore_session()` are cached
too — the boto3 client is built **once per process**. With the default chain this is fine
(botocore's IMDS/container providers refresh credentials transparently). With explicitly
passed static creds it will **not** refresh past the ~6h STS expiry — a long-running service
would eventually fail. This is an extra reason to prefer the default chain (Option A below).

## 4. The options `osbot-aws` already gives us

### Option A — Use the default credential chain (don't pass keys at all) — *recommended*

This is already how `S3()` behaves with default kwargs (all `None`). When no credentials are
passed, `boto3.client('s3')` uses botocore's default provider chain, which reads
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` **and `AWS_SESSION_TOKEN`** from env itself —
so **all three modes work, with auto-refresh** for role/STS creds.

- **Change required:** ensure nothing explicitly populates `Session__Kwargs__S3` with
  env-read keys (the offending injection, if any, is upstream — see §6).
- **osbot-aws code change:** none.
- **Covers:** modes 1, 2, 3 + auto-refresh.
- **Trade-off:** depends on confirming/removing the upstream injection.

### Option B — Add `aws_session_token` plumbing to the existing path

Add an `aws_session_token` field to `Session__Kwargs`, thread it through `client_boto3()`
(`if aws_session_token: client_kwargs['aws_session_token'] = …`), sourced from
`AWS_SESSION_TOKEN`.

- **Change required:** edit `osbot-aws` core (`Session__Kwargs.py`, `apis/Session.py`).
- **Covers:** makes *explicit* credential passing correct for mode 3.
- **Trade-off:** more invasive; touches a shared upstream library; does not address
  auto-refresh for static creds.

### Option C — Route the S3 client through the existing `botocore_session()`

`osbot_aws/apis/Session.py:28` already has a token-aware session builder:
```python
def botocore_session(self, aws_access_key_id=None, aws_secret_access_key=None,
                     aws_session_token=None, region_name=None, ...):
    session = boto3.Session(**kwargs)   # includes aws_session_token
```
It **exists but is not wired into the S3 path** (S3 uses `client_boto3`, the token-less
builder). Option C = have the S3 client use this method instead.

- **Change required:** re-wire `S3.client()` / `client_boto3()` in `osbot-aws`.
- **Covers:** mode 3 via the already-present token support.
- **Trade-off:** touches osbot-aws; two parallel session builders should ideally be unified.

### Recommendation

**Option A** is cleanest — it fixes all three modes and auto-refresh with the least code, and
requires no change to the shared `osbot-aws` library. Fall back to **Option C** (or **A + B**)
only if the cache layer genuinely needs to pass explicit temporary credentials rather than
letting boto3 resolve them.

## 5. What this repo can actually do (levers available here)

This repo does not construct boto3 clients, so the substantive fix is downstream. From here
the available levers are:

1. **Dependency pinning** — `pyproject.toml:21` declares `mgraph-ai-service-cache-client = "*"`
   (and `osbot-aws` is transitive). Once an upstream fix lands, pin to the patched versions.
2. **Runtime env hygiene** — ensure the deploy/run env does not inject misleading
   `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` values. `Deploy__Service.py` does not set any
   AWS credential vars today; the container/EC2 runtime is responsible.
3. **Startup diagnostics** (optional, recommended by the brief §5.4) — log the resolved
   credential source at startup (e.g. via `STS().caller_identity_arn()`), without leaking
   secrets, so a misconfiguration is a one-line log rather than a multi-hour live debug.

## 6. Open gap before a fix can be scoped precisely

`mgraph-ai-service-cache-client` / `mgraph-ai-service-cache` could not be pulled in the
analysis environment (they require Python ≥3.12). The one unconfirmed question is **whether
that layer reads `AWS_*` from env and explicitly populates `Session__Kwargs__S3`** (which
would explain a mode-1 failure despite osbot-aws's truthiness guards). Confirming this — by
inspecting the cache-client's S3-client construction on a Python 3.12 environment — is the
prerequisite to choosing between Option A (remove the injection) and Option B/C (fix the
token path).

## 7. Acceptance criteria (for whoever implements the fix)

| Env in container | Expected |
|------------------|----------|
| no `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`, IMDS/role available | ✅ works (mode 1) |
| `AWS_ACCESS_KEY_ID=""` + `AWS_SECRET_ACCESS_KEY=""`, IMDS available | ✅ works — empty treated as unset (mode 1) |
| long-lived `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` | ✅ works (mode 2) |
| `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` + `AWS_SESSION_TOKEN` | ✅ works (mode 3) |
| no credentials resolvable anywhere | ❌ fails with a clear error naming the bucket + "no AWS credentials resolved" |
| `AWS_ACCOUNT_ID` absent | ✅ still works (derive via STS or treat as optional) |

Plus: under mode 1, a long-running service must keep working past the ~6h credential expiry
(the default chain auto-refreshes; explicitly passed static creds do not).
